# 自動送出メール文面集（個展なび）

サイトからユーザーへ自動送出するメール（申込受付・機能付与完了・取引各フェーズ通知 等）の**文面の単一ソース**。UI と同じく「捕捉は決定時、構造化は後」の原則で、確定した発火点から順に文面を起こして追記していく（完成後にまとめて作らない）。

## 位置づけ・進め方

- **本番実装は Drupal（バックエンド）が送出**する。本ファイルは Drupal 実装フェーズへ渡す**文面と発火条件の仕様**であり、HTML/CSS のメールテンプレート実装そのものではない。
- **まずプレーンテキスト文面を確定する**。装飾HTMLメール化は Drupal フェーズで別途行う（プレーンが常に fallback として要るため先に固める）。
- 文面中の可変値は **`{{token}}` プレースホルダー**で書く（下記「トークン規約」）。
- 1通ごとに「発火点／受信者／トリガー／件名／本文」をワンセットで書く。**発火点の棚卸し（下表）が index、各文面が本体**。
- サイト内の状態名・期限呼称・ページ呼称は **CLAUDE.md / docs/transaction-states.md が canonical**。メール文面もそれに従い、独自の言い換えをしない（例：状態名「購入確定待ち」、期限呼称「確定期限」）。

### ユーザーが選べるメール（P5-13 メール通知設定・2026-09-26 確定）

旧システムのユーザー向けメール設定（旧1〜5）を下記①〜⑤へ整理した。**P5-13 で停止できるのはこの5種類だけ**。アカウント系・送信フォーム系・機能申込系・取引系・A-04 重要なお知らせは**必ず届く**（停止できない）。設定の置き場所は **P5-13 に一本化**（P3-13／P4-13 のオーディエンス画面はスイッチを持たず、P5-13 へのリンクだけ）。

**P5-13 の区分**：「ユーザーとして受け取るメール」（①②③・全ユーザー）／「クリエイター／ギャラリーとして受け取るメール」（④⑤・その機能を利用中の人だけ表示）／「必ずお届けするメール」（停止できない4種類の説明のみ）。各項目に配信タイミング（1日1回・随時・月1回）を表示する。

**① リマインダーの細則**
- 「今日から開催／もうすぐ開催／もうすぐ終了」の判定は、サイトの開催ステータス（`.sb-*`：開催中・もうすぐ開始・もうすぐ終了）と同じ基準を使う（メール独自の日数を持たない）。
- **同じ展覧会が複数日にわたって届いてよい**（「もうすぐ終了」の期間中は毎日載る）。ユーザー判断：旧 daily mail が嫌われたのは、ウォッチも興味あり！もしていない＝アクションをしていないユーザーに毎日届いたため。自分でウォッチ・興味あり！した展覧会のリマインドは、繰り返し届いても役に立つ。
- ウォッチ中の展覧会と「興味あり！」の展覧会が重なる場合、同じメールには**1回だけ**載せる。
- 旧 daily mail にあった「開催中の展覧会すべて」と「ピックアップ展覧会（ウォッチ0件の人向け）」は廃止。ウォッチ0件の人への案内は P5（myページ）のゼロ状態の表示が担う。

**② ウォッチ新着の細則**
- **作品は対象外**：LIAISON／LIAISON+ では作品を頻繁に追加・取り下げするため、通知すると通数が読めず、取り下げた作品の通知も届いてしまう。
- **記事は展覧会の会期に関係なく必ず通知する**（会期後のお礼の記事など、アーカイブの展覧会に記事が載ることがあるため）。
- 会期が終わった展覧会を後から登録した場合（アーカイブ目的）、その**展覧会自体の公開通知は送らない**。

**③ ニュース・キャンペーンの細則**
- 送るかどうかは**事務局が1件ずつ選ぶ**（P61-11「登録ユーザーにメールでも送る」のチェック）。お知らせを公開するたびに自動では送らない（通数が増えすぎないように）。
- 配信先は P61-11 の「対象」で決める。ゲストにはメールを送れないため、**「全員」「ユーザー」はどちらも登録ユーザー全員**（ユーザーロールが土台なので、クリエイター・ギャラリーにも届く）。**「クリエイター・ギャラリー」はその機能を利用中の人だけ**に絞る。どの対象でも、受け取るかどうかは③の1つの設定で決まる。
- カテゴリ「重要」のお知らせは③ではなく A-04（停止できない）として送る。P61-11 の説明文はカテゴリ・対象の組み合わせで「誰に届くか」を出し分ける。
- **広告にあたるメールは事前の同意が必要**（特定電子メール法）なので、**既定はオフ**。新規登録（P11-1）に任意のチェック「個展なびからのニュース・キャンペーンのメールを受け取る」を置き、チェックした人だけオンにする。

**旧設定からの移行**
- ① リマインダー＝旧1）daily mail **または**旧3）興味あり！のどちらかがオンならオン（片方だけ引き継ぐと、もう片方で受け取っていた通知が届かなくなるため）。
- ② ウォッチ新着・④・⑤＝旧設定をそのまま引き継ぐ。
- ③ ニュース・キャンペーン＝新設のため、同意の記録が無い既存ユーザーはオフ。

- ウォッチ対象は**クリエイター・ギャラリーのみ**（CAP-10）。展覧会・記事は「公開された内容」＝通知のトリガーであってウォッチ対象ではない。

## 文面 — U-07 メールアドレス変更手続きのお知らせ（旧アドレス宛・自動・即時）

- **発火：** P5-11 のログインID（メールアドレス）欄で「確認メールを送る」を押した直後（自動送出）。新アドレスへの確認メール（U-06）と同時に、**現在の（旧）アドレス**へ送る。
- **受信者：** 本人（旧アドレス）
- **目的：** 乗っ取った第三者がログインIDを自分のアドレスに変えると、本人は以後のお知らせを受け取れなくなる。変更が確定する前に、本人が気づいて止められるようにする。新アドレスは一部を伏せ字にする（`{{maskedNewEmail}}`）。
- 画面側：P5-11 の説明「あわせて、現在のアドレスにも変更手続きがあったことをお知らせします」、送信後の表示「現在のアドレスにも、変更手続きのお知らせを送りました」。

```
件名：【個展なび】メールアドレスの変更手続きがありました

{{userName}} 様

変更手続きがありました。

──────────────────────────────
```

## 追記時のルール

- 新しい発火点が確定したら、まず上の**インベントリ表に1行追加**（状態＝未着手）。文面を起こしたら「起草済」に更新し、本文セクションを追記する。
- 状態名・期限・ページ呼称は CLAUDE.md / transaction-states.md を参照し、**メール独自の言い換えをしない**。
- 画面（`KTN.submitDone()` モーダル・`.ktn-txn-alert` 等）とメールで、同じイベントの表現・期限値を食い違わせない。
- Drupal 実装フェーズで、共通ヘッダー/フッター部品・トークン差し込み・HTMLメール化を行う。本ファイルはその入力仕様。
