# メールテンプレート管理システム（P90-9）仕様

管理者が送信する通知・確認メールの文面を、画面ごとのハードコードから**P90-9（管理者-メールテンプレート管理）が一元管理するテンプレートデータ**へ切り出すための仕様。P90-2（クリエイター/ギャラリー機能申込管理）を最初の適用対象として設計・実装する。将来、他の管理者送信画面（P90-11のリエゾンプラス申込審査、取引デスク等）を追加する際も本仕様を土台にする。

## 1. 位置づけ

- `docs/email-templates.md`＝**発火点（いつ・誰に送るか）の棚卸しとDrupal引き継ぎ用の文面インデックス**（M-01〜等の通し番号）。canonicalなのは「どのイベントでどの受信者に送るか」の一覧性。
- 本ファイル＋P90-9＝**文面の実体を編集可能なデータとして持つ仕組み**の仕様。email-templates.mdのM番号は「発火点インデックス」として残し、本ファイルの`variantKey`と対応付ける（4章）。
- 現段階（HTML/CSS/JS納品・React CSR化前）は**ページ間の実データ連携がない**（各HTMLが独立ロード）。そのためP90-9のテンプレートCRUDと、P90-2側で使うテンプレート選択は、**同じ形のデータをそれぞれのページ内デモ配列として個別に持つ**（本番はDrupalのテンプレートAPIに統合）。

## 2. データモデル

テンプレート1件のフィールド：

| フィールド | 内容 | 備考 |
|---|---|---|
| `id` | 内部一意ID | 削除・編集しても不変。表示用の管理画面内番号とは別 |
| `screenId` | 使用する管理画面のページID（例：`p90-2`） | 送信元画面ごとに束ねる単位 |
| `screenLabel` | 画面の表示名（例：「クリエイター/ギャラリー機能申込管理」） | 一覧のフィルタ・列表示用 |
| `pattern` | `normal`（正常系）／`abnormal`（非正常系） | 画面ごとに2区分固定。正常系＝主目的が達成された時の通知、非正常系＝確認・取消など主目的が達成されなかった/保留された時の通知 |
| `variantKey` | 画面側だけが解釈する任意の識別子文字列 | P90-9はこの値を**不透明な文字列として保存するだけ**（意味を解釈しない）。命名規則は画面側の自由（4章に実例） |
| `name` | テンプレート名（一覧の主表示・プルダウンの選択肢テキスト） | 例：「入力不足・入力誤り」「クリエイター機能 – 新規ページ作成」 |
| `subject` | 件名 | 本文と分離した独立フィールド（旧：本文内に「件名：」の1行として埋め込み→廃止） |
| `body` | 本文（`{{token}}`プレースホルダー使用可） | トークン規約は`docs/email-templates.md`のものをそのまま使う |
| `status` | `active`／`archived` | 削除は原則archived止まり（5章） |
| `usageNote` | 管理者向け補足（いつ使うか） | 一覧・編集画面にのみ表示。送信画面のプレビューには出さない |
| `updatedAt` | 最終更新日時 | デモでは`todayLabel()`相当を保存時に付与 |

### パターン区分の呼称について

UIラベル・会話では「正常パターン／確認パターン」のような言い方をすることがあるが、**データ上の区分は「正常系（`normal`）／非正常系（`abnormal`）」の2値**である。非正常系には「申込者に確認する」（返信を待つ問い合わせ）と「取消にする」（取消のご連絡）の両方を含む——どちらも「主目的（機能付与）が今回は成立しなかった/保留された」という共通の性質を持つため。

## 3. 役割分担の判断軸：トークン置換 vs バリアント分割

同じ画面・同じパターン内でも、分岐要因（例：申込ロール＝クリエイター/ギャラリー）を**トークン置換**で吸収するか、**別テンプレート（バリアント）に分割**するかは、以下の判断軸で決める：

- **本文の構成そのものは変わらず、語句の一部だけが変わる**（例：「クリエイター機能」⇔「ギャラリー機能」という名詞1点のみ） → トークン置換（`{{roleName}}`等）。1テンプレートで両方をカバーする。
- **文面の構成・内容そのものが変わりうる**（例：新規作成なら無い「引き継ぎ結果」ブロックが既存リンク付けにだけ入る。将来的にクリエイター向け・ギャラリー向けで案内文の内容自体を書き分けたい） → バリアント分割。編集は完全に独立、平文のまま自由に書ける（P90-9の編集画面に条件分岐構文を持たせない）。

P90-2では、正常系（利用開始のご案内）は**ロール×処理種別で内容が実質的に分岐しうる**ためバリアント分割、非正常系（確認・取消）は**理由（reason）ごとに文面が分岐するがロールは名詞1点の置換に留まる**ためロールはトークン、理由はバリアント分割、という組み合わせにする（4章に一覧）。

## 4. P90-2 への適用（テンプレート一覧・確定版）

### 正常系（4件・ロール×処理種別で完全分割）

| `variantKey` | `name` | 対応するM番号 |
|---|---|---|
| `creator-new` | クリエイター機能 – 新規ページ作成 | M-02（新規） |
| `creator-link` | クリエイター機能 – 既存ページのリンク付け | M-02（既存リンク・引き継ぎ結果ブロック付き） |
| `gallery-new` | ギャラリー機能 – 新規ページ作成 | M-04（新規・新規起草） |
| `gallery-link` | ギャラリー機能 – 既存ページのリンク付け | M-04（既存リンク・新規起草） |

P90-2側は、申込の`role`＋`processType`から`variantKey`（`{role}-{processType}`）を算出し、パネルを開いた時点でこれをデフォルト選択する（プルダウン自体は4件とも見えるため手動で他の文面に差し替えることも可能）。

### 非正常系・確認メール（2件・理由ごとに分割／ロールは`{{roleName}}`トークン）

| `variantKey` | `name` | 対応するM番号 |
|---|---|---|
| `confirm-input-error` | 入力不足・入力誤り | M-06 パターン① |
| `confirm-duplicate` | 重複申込の可能性 | M-06 パターン② |

※`role-switch`は申込者本人からの連絡が起点のため確認メールを経由しないことがある（既存のCLAUDE.md運用どおり）。確認メールの選択肢には含めない。

### 非正常系・取消のご連絡（4件・理由ごとに分割／ロールは`{{roleName}}`トークン）

| `variantKey` | `name` | 対応するM番号 |
|---|---|---|
| `cancel-input-error` | 入力不足・入力誤り | M-07 パターン①（共通文） |
| `cancel-duplicate` | 以前に別アカウントで申込済み | M-07 パターン①（共通文） |
| `cancel-role-switch` | 希望ロールの変更 | M-07 パターン② |
| `cancel-other` | その他 | M-07 パターン①（共通文） |

`input-error`／`duplicate`／`other`は現状すべて同じ文面（今回の移行では文面の新規作成は行わず、現行コードの出力をそのままテンプレート化する）。バリアントとして分けておくことで、将来それぞれの文言を個別に調整できるようにする（分割の目的そのもの）。

### `variantKey`命名規約（画面側の自由記述だが、P90-2ではこの規則）

- 正常系：`{role}-{processType}`（例：`creator-new`）
- 非正常系・確認：`confirm-{reason}`
- 非正常系・取消：`cancel-{reason}`
- 管理者がP90-2の送信パネルからその場で追加したカスタムテンプレートは、`confirm-{timestamp}`のように追加時に一意な値を自動採番する（4章の命名規則が使えない自由入力名のテンプレートのため）。

## 4.1 P90-11 への適用（テンプレート一覧・確定版）

P90-11-1（本人確認審査）は、P90-2と違い正常系・非正常系ともに**分岐要因を持たない**（申込ロールによる文面分岐なし・理由は複数選択のチェックボックスであってバリアントではない）。そのため`screenId:'p90-11'`のテンプレートは正常系1件・非正常系1件の**計2件のみ**で足りる。

| `variantKey` | `pattern` | `name` |
|---|---|---|
| `invite` | `normal` | 本人確認OKのご案内（Step2へ） |
| `return` | `abnormal` | 差し戻しのご連絡 |

### `variantKey`命名規約（P90-11）

- 正常系：`invite`固定（分岐なしのため1本）
- 非正常系：`return`固定（同上）
- 管理者がP90-11-1の送信パネルからその場で追加したカスタムテンプレートは、`invite-custom-{timestamp}`／`return-custom-{timestamp}`のように追加時に一意な値を自動採番する（P90-2の`confirm-{timestamp}`と同じ考え方）。

### `{{reasonsList}}`：複数選択チェックボックスUIとテンプレートモデルの橋渡し

P90-11-1の差し戻しパネルは、差し戻し理由を**複数選択可能なチェックボックス＋補足自由記述**というUIのまま維持する（P90-9導入前からのUXを変更しない）。これは「1 `variantKey` = 1テンプレート」というP90-9のモデルと直接には噛み合わない（理由の組み合わせ数だけバリアントを作るのは非現実的）。

この橋渡しとして、`return`テンプレートの本文には通常の`{{token}}`と同様に`{{reasonsList}}`という**計算プレースホルダー**を埋め込む。P90-9側はこれを他のトークンと区別せず不透明な文字列として保存するだけだが、送信側（P90-11-1コントローラ）は送信直前に選択されたチェックボックス＋補足テキストから`D.reasonsListText(checked, detail)`で整形済みテキストを生成し、`tokens.reasonsList`として他のトークンと一緒に`D.applyTokens(t.body, tokens)`へ渡す。

この方式により、P90-9の編集画面・データモデルに条件分岐構文を持ち込まずに、既存の複数選択UXをそのまま活かせる。**同様の「UIは複数選択だが文面は1テンプレート」というケースが他画面で発生した場合も、専用の計算トークンを1つ追加する形で対応する**（バリアント分割はしない）。

## 5. P90-9（メールテンプレート管理）画面仕様

- **形式**：`mgmt-page p90-9-page`、`data-w="detail"`（760px統一）、`.ktn-mgmt-wrap.ktn-mgmt-stack`。P90-2同様、オーナーを持たない管理者専用ページのため`.ktn-mgmt-context`は付けない（`.ktn-content`直下に`.ktn-mgmt-wrap`）。
- **一覧**：画面（`screenLabel`）／パターン（正常系・非正常系）でフィルタ。行にテンプレート名・画面名・パターンバッジ・更新日・状態（有効/廃止）・編集/削除ボタン。`KTN.pagination.render`で共通ページング。
- **パターンバッジ**：`.cb-content`系のformを流用し新規バリアントを追加（正常系＝緑系`.cb-article`の色を踏襲／非正常系＝amber系`.cb-review`の色を踏襲。バッジ設計システムの既存パレットに寄せ、新規の色相を増やさない）。
- **新規追加／編集**：画面選択・パターン選択・`variantKey`・テンプレート名・件名・本文（`{{token}}`一覧をヘルプとして併記）・補足メモ。`.p211-field`/`.p211-input`/`.p211-select`/`.p211-textarea`を再利用。
- **削除**：**個々のテンプレートの使用実績（ログ）は判定しない**。削除操作は即座に一覧から取り除く論理削除（`status:'archived'`）とし、確認モーダルは既存の`.p319-del-modal`（p3-19等で使用中の共通削除確認モーダル）をそのまま流用する。物理削除・完全消去のUIは持たない（archivedの一覧からの復元は将来検討）。
- **削除ガード（区分の最後の1件は削除不可）**：送信画面側は「画面ID＋パターン／`variantKey`プレフィックスで決まる区分（category）」を固定的に参照する（例：P90-2の「ご利用開始のご案内」パネルは`screenId:'p90-2', pattern:'normal'`区分、確認メールパネルは`variantKey`プレフィックス`confirm-`区分、取消メールパネルは`cancel-`区分）。この区分定義は**テンプレートの残数ではなく画面のコード構造そのもの**から決まる固定情報のため、P90-9側は`SCREEN_REQUIRED_CATEGORIES`（`kotennavi-pages.js`内、画面ID→区分リストの静的マップ）として個別に保持する。削除しようとしているテンプレートがいずれかの必須区分に該当し、かつ同区分内で有効（`active`）なテンプレートが自身1件のみの場合、削除確認モーダルは「この操作は行えません」表示に切り替わり（削除ボタンを隠し、キャンセルボタンを「閉じる」に変更）、区分ラベル・画面名を明示した警告文を出す。これにより送信画面のパネルが空になる状態を未然に防ぐ。新規画面をP90-9のテンプレート方式に対応させる際は、その画面の送信パネル構成に合わせて`SCREEN_REQUIRED_CATEGORIES`にエントリを追加すること。

## 6. P90-2 側の連携仕様

- 既存の「確認理由」「取消理由」プルダウン（`p902InquiryReasonSel`／`p902CancelReasonSel`）を、**そのままテンプレート選択プルダウンとして再利用**する（値＝`variantKey`のバリアント部分）。末尾に「＋ 新しいテンプレートとして追加」を追加。
- 「ご利用開始のご案内メール」パネルには新たにテンプレート選択プルダウン（正常系4件）を追加し、申込の`role`＋`processType`から算出した`variantKey`をデフォルト選択する。
- いずれのパネルも、選択したテンプレートの`subject`/`body`をトークン展開して**件名入力欄＋本文テキストエリアの2フィールド**に流し込む（件名の独立フィールド化）。送信前に自由編集可能な点は従来どおり。
- 「＋ 新しいテンプレートとして追加」を選ぶと、テンプレート名の入力欄が現れる。名前を入力して保存すると、その時点で編集中の件名・本文がP90-2内のローカルテンプレート配列に新規追加され（画面遷移なし）、プルダウンの選択肢にも即座に反映される。

## 8. 今後の拡張

- P90-11（リエゾンプラス機能申込審査）は2026-08-10に適用済み（4.1章）。取引デスク等、他の管理者送信画面を追加する際は、`screenId`を追加し、その画面固有の`variantKey`命名規約を本ファイル4章・4.1章と同様の形で追記する。
- P90-9自体は画面・パターンを問わない汎用CRUD画面のまま維持し、`variantKey`の意味解釈を持たない（画面側の責務）。
- P90-9の一覧表示は2026-08-10に`<ul class="p319-list">`のカード形式から**テーブル形式**（`.p315-archive-table`共有・列＝パターン／使用画面・識別キー／テンプレート名／更新日／状態／操作）へ変更済み。行クリックでの遷移は無いため`.p902-table`（行クリック用スタイル）は使わない。
- 自動送信（可視化）タブの一覧も同日、カテゴリごとの`.p909-auto-row`カード積みからカテゴリごとの**テーブル**（列＝ID／発火イベント／対象・トリガー元・タイミング／件名／更新日／操作＝2026-08-11の更新日列追加後）へ変更済み。セルクラス（`.p909-cell--title`/`.p909-cell--meta`/`.p909-cell--muted`/`.p909-cell--actions`）は手動送信タブと共有し、カテゴリ見出し（`.p909-auto-group__title`）はテーブルの上に残す。
- 「＋ 新規テンプレート」ボタン（`.p909-toolbar-row`）はタブナビの直下（画面・パターンのフィルター行より上）に固定配置する。フィルター行の下・表の上に置くと折返し時にフィルターや表のタイトル行と視覚的に重なるため、タブ直下に置くレイアウトを標準とする。
- **自動送信タブの「状態／起草進捗」列は2026-08-11に完全撤去した**：一度は「制作フェーズの進捗チェックリスト」として明示する方向（列見出しを「起草進捗」に変更＋`title`注記）で対応したが、ユーザーが編集モーダルを開いて直接トグルする操作が無いことに気づき、「本番フェーズでは必要ないので不要」と判断。管理・編集する手段を持たない自動判定バッジを列として置き続ける意味が無いため、`autoStatus()`／`AUTO_STATUS_LABEL`／`AUTO_STATUS_CLS`ごと削除した。件名の入力有無は「件名」列自体の表示（未入力時は「—」）で代替できるため、別列としての状態表示は不要という結論。
- **自動送信タブに「＋ 発火点を追加」ボタン＋カテゴリフィルターを2026-08-11に追加**：ユーザー要望「自動送信には新規作成ボタンとフィルターがほしい」を受け、手動送信タブと同じ`.p909-toolbar-row`＋`.p319-toolbar`/`.p319-filter`/`.p319-empty`（既存クラスを再利用・新規CSSなし）を配置。カテゴリ（機能申込系／取引系／アクティビティ系）フィルターは`renderAuto()`内で`AUTO_TRIGGERS`を絞り込み、非該当カテゴリのテーブルごと非表示にする（1件も無ければ`#p909AutoEmpty`を表示）。「発火点を追加」は新規モーダル`#p909AutoNewModal`（ID／カテゴリ／発火イベント／対象／トリガー元／タイミング／件名／本文／補足メモの全項目を入力可能）から`AUTO_TRIGGERS`へ`push`する。**既存行の「編集」モーダル（`#p909AutoEditModal`）は仕様を変えず件名・本文・補足メモのみ編集可能のまま**（ID／カテゴリ等のメタ情報はdocs/email-templates.mdの発火点インベントリと対応させる識別情報のため、登録後の書き換えは想定しない。新規追加時のみ全項目を確定させる設計）。
- **自動送信タブのカテゴリ別テーブルの列位置を2026-08-11に`table-layout:fixed`で統一**：カテゴリごとに独立した`<table>`が既定（auto）で個別に列幅を決めていたため列位置が表ごとにずれていた。`.p909-auto-table{table-layout:fixed}`＋列幅の明示指定（件名列のみ幅指定なしで残り幅を吸収）で3表とも同じx位置に揃えた。
- **自動送信タブに更新日列・削除ボタンを2026-08-11に追加／操作ボタンを縦並びに統一**：ユーザー指示「更新日と削除ボタンを追加してください。削除ボタンは編集ボタンと縦並びにしてください。手動送信と共通です。また削除ボタンを押したとき確認モダールを出してください。」を受け、`AUTO_TRIGGERS`各行に`updatedAt`を追加しテーブルへ「更新日」列（件名の後・操作の前）を追加。編集・削除ボタンは新設の共通ラッパー`.p909-actions-stack`（`display:flex;flex-direction:column;gap:6px`）で縦並びにし、**手動送信タブの操作セルも同じラッパーへ統一**（従来の`margin-left`横並びを廃止）。削除確認は新規モーダルを作らず手動送信タブの既存`#p909DelModal`を共用（`openDelModal(t, type)`の`type`引数で分岐）。手動送信＝論理削除（`status:'archived'`）のまま、自動送信＝物理削除（`AUTO_TRIGGERS`から`splice`）という非対称は、自動送信の発火点が`docs/email-templates.md`インベントリとの対応そのものであり不要になれば行自体を無くしてよい性質のため。詳細は`docs/handoff-decisions.md`追補185。
