# Stripe Connect アカウント種別比較（社内資料）

LIAISON+ の代金回収・精算（Stripe Connect）実装にあたり検討した3つのアカウント種別（Standard / Express / Custom）の比較資料。**結論＝Express採用確定**（2026-07-27・詳細は `docs/handoff-decisions.md` 追補㉞）。本ファイルは判断の前提となった比較内容を独立した参照資料としてまとめたもの。

---

## 1. 前提となった絶対条件

> creator/gallery に Stripe との直接契約・操作を要求しない。
> 要求した時点で操作できる人が激減し、サービス利用者がほぼいなくなることを最も懸念する。

この条件により、出品者が自分名義のStripeアカウントを完全に自律運用する方式（後述Standard）は検討の初期段階で除外される。

また、CLAUDE.md 既定の方針として以下も前提：

- 「Stripe決済手数料-実質マージンは利用者には非公開」
- サービス利用料は「作品の販売価格＋送料＋梱包費」の合計に対して計算し、Stripe決済手数料はサービス利用料に内包（出品者の別途負担なし）
- 振込：月末締め・翌月20日払い（20日が金融機関休業日の場合は翌営業日）・振込手数料は利用者負担

## 2. 3モデルの概要

| | Standard | Express | Custom |
|---|---|---|---|
| Stripeアカウントの所有者 | 出品者自身（自分のStripeアカウントを持つ） | 出品者名義だが個展なびが管理 | 出品者名義だが個展なびが完全管理 |
| 出品者に見えるStripe UI | フルのStripeダッシュボード | 簡易版Expressダッシュボードのみ | **一切なし**（個展なびの画面のみ） |
| 資金の流れ | Direct Charge（購入者の支払いが出品者のStripe残高に直接入る） | Separate Charges and Transfers（個展なびのStripe残高に一旦入り、精算日にTransferで送金） | 同左（Separate Charges and Transfers） |
| 入金スケジュールの制御 | 出品者自身がダッシュボードで設定 | 個展なびがAPIで制御 | 個展なびがAPIで制御 |
| 手数料の可視性 | 出品者がStripeの生の手数料内訳を見られる | 個展なびが完全に管理・非公開にできる | 同左 |
| オンボーディング | 出品者がStripeアカウントを自分で開設 | Stripeホスト画面へ一度リダイレクト、規約同意・情報入力 | 個展なびの自前UIのみ（画面はすべて個展なびが作る） |
| 本人確認（KYC）審査 | Stripeが実施、出品者とStripeが直接やり取り | Stripeが実施、UIはStripeホスト画面 | Stripeが審査するが、UI・書類収集・結果反映は個展なびが自前で実装 |
| Stripeからの直接連絡 | 通常運用 | 稀にあり（再確認・規制対応時、個展なびを介さず直接メール） | 基本的になし（個展なびが窓口） |

---

## 3. 出品者（creator/gallery）が必要とする操作・意識の比較

### Standard
- 自分名義でStripeアカウントを開設し、以後の入金設定・ダッシュボード確認を自分で行う
- Stripeの手数料内訳・入金明細を直接閲覧できてしまう（非公開方針と矛盾）
- **→ 前提条件（Stripe直接操作の禁止）に反するため不採用**

### Express
- **①初回申込み時**：個展なびのオンボーディングフォーム（本名・フリガナ・生年月日・住所・電話番号等）入力後、**Stripeホスト画面へ一度だけ遷移**し「Connected Account Agreement」への同意（＋必要に応じ本人確認書類のアップロード）を行う。この1回のみがStripe側の直接操作。
- **②通常利用中**：個展なびの画面（p3-17等）で残高確認・精算設定・口座情報変更が完結。Stripe画面へ戻る必要は基本的にない。
- **③隠れた接点**：Stripeがリスク判定や規制要件で再確認が必要と判断した場合、個展なびを介さず出品者へ直接メールが届くことがある（頻度は低い・個展なびの制御外）。銀行口座変更等の軽微な更新はAPI経由（個展なびの画面内）で完結できる場合もあるが、本人確認情報の変更は再度Stripeホスト画面に戻る必要が生じることがある。

### Custom
- 出品者がStripe画面を見ることは一切ない。すべて個展なびの画面で完結。
- 裏返しとして、本人確認書類の収集・審査結果の反映・再確認対応・機微情報のAPI送信をすべて個展なびが自前で実装・運用する必要がある（次項で詳述）。

## 4. 精算方式・必要情報の違い（Standard vs Express/Custom）

| | Standard | Express / Custom |
|---|---|---|
| 精算のトリガー | 出品者が自分でStripeダッシュボードから設定・確認 | 個展なびが月次バッチで一括精算（p3-17で確定：毎月固定日・オンデマンド精算なし） |
| 振込手数料 | Stripeの標準控除がそのまま出品者に見える | 個展なびが計算・提示（出品者負担である点は同じだが、内訳は個展なびの画面のみで完結） |
| 精算下限額 | 出品者が自分のダッシュボードで設定 | 個展なびの画面でプリセット選択（¥1,000〜¥100,000・自由入力不可） |
| 出品者が入力する情報 | Stripeのオンボーディングフォーム（Stripe側UI） | 個展なびのフォーム（p3-11/p11-4等）＋Expressのみ初回同意画面 |
| サービス利用料の非公開方針 | **維持できない**（生の手数料が見える） | 維持できる |

**結論**：Standardは精算の主導権が出品者側のStripeダッシュボードに移り、個展なびの「サービス利用料として一体で見せる」設計思想そのものと衝突する。Express/Customはどちらも個展なびが精算ロジックを完全に握れる点で共通。

---

## 5. Customを選んだ場合に個展なびが負う継続的責任（Expressとの決定的な差）

Expressとの本質的な違いは「実装コストが1回で済むか」ではなく、**運用フェーズで個展なびがKYCの一次窓口であり続けるか**という点にある。

| 領域 | 内容 |
|---|---|
| 審査結果の受け皿 | Stripeからの承認/却下/追加書類要求を、個展なび独自のUI・運用フローで出品者に伝える窓口が必要。却下理由の説明・問い合わせ対応も個展なびのサポート業務になる（Expressなら一部はStripe側に流れる） |
| 機微情報の取り扱い責任 | 本人確認書類（運転免許証等）の画像を個展なびのUI/サーバーで一時的にでも受け取りStripe APIへ送信する実装が必要。個人情報保護法上の「取得」に該当し、保管期間・漏洩時の責任主体が個展なびになる（Expressなら書類はStripeホスト画面へ直接アップロードされ、個展なびのサーバーを経由しない） |
| 再確認対応の継続保守 | Stripeは規制変化・リスクスコア変動等で随時追加情報を要求してくる。Customでは「Stripeが何を求めているか」を検知し、都度個展なびの画面上に導線を作る仕組みを恒常的に保守する必要がある（Stripe側要件の変化に個展なびが追従し続けるコスト） |
| 法的立場のグレーさ | Customは外形上Stripeブランド画面が一切出ないため、規制当局や紛争時に個展なびが実質的なKYC主体・資金移動業とみなされるリスクがゼロではない。Expressは「Stripeの管理下にあるアカウント」という外形が保たれやすい |
| 法人（ギャラリー）対応 | 法人番号・登記情報等、Stripeが法人アカウントに求める追加情報の収集フォーム・検証ロジックを個展なびが用意し続ける必要がある（Expressでも別課題として残るが、UI自体はStripe側が可変的に出し分けてくれる） |

**非対称性**：Expressの負担は「初回同意1回＋稀な直接メール」という**上限のある摩擦**。Customの負担は「運用フェーズに際限なく積み上がる構造的負担」。小規模運営体制では後者のリスクが相対的に大きい。Stripe公式もCustomはコンプライアンス専任リソースを持つ大規模プラットフォーム向けと案内している。

---

## 6. 結論と緩和策

**採用：Express**

- Standard：出品者への直接操作要求が絶対条件に反するため除外
- Custom：継続的なKYC運用・機微情報取り扱い・法的リスクが小規模体制に対して非対称に重いため除外
- Express：出品者の接点を「初回同意1回＋稀な直接メール」に限定でき、非公開方針・精算主導権も維持できるためこれを採用

**Express唯一のネック（Stripe同意画面が一度出ること）への緩和策**：
Stripe Connect embedded onboarding（プラットフォームのブランド・配色を反映できる埋め込みUI）を利用することで、離脱率を抑えられる見込み。同意文言自体はStripe標準のまま残るが、画面の統一感は保てる。

## 7. 既存ページへの実装含意

### 反映済み（2026-07-27・追補㉟）

Expressを採用した以上、「Stripeを一切意識させない」は完全には成立しないため、最小限の意識づけとFAQ対応を実ページへ反映済み。

- **`kotennavi-p11-4.html`**：「本人確認・振込先口座が必要な理由」に3項目目「決済パートナーとの連携」を追加。Stripeへの振込処理委託・初回のみの簡単な連携手続き・通常操作は個展なび画面内で完結する旨を明記。
- **FAQ（`KTN.QA`・`kotennavi-common.js`）**：
  - `liaisonplus-apply`（申込時）に LAP-12「Stripeという名前が出てきました。個展なびとは別のサービスですか？」を追加。
  - `liaison-settlement`（運用中・p3-17/p4-17）に SET-07「Stripeから直接メールが届きました。対応が必要ですか？」・SET-08「Stripeのアカウントを自分で管理する必要がありますか？」を追加。
  - 役割分担：初回の疑問＝申込時カテゴリ、運用中に実際に遭遇したときの対応＝精算カテゴリ、と参照タイミングで分離し内容の重複を避けた。
- **`kotennavi-p11-4.html`（LIAISON+利用規約〔抜粋〕）**：新規**第4条（決済代行サービスの利用）**を新設し、Stripe, Inc.及びその関連会社への決済処理委託・出品者が決済代行会社所定の手続きに応じる義務・登録情報の提供範囲を明記。旧第4条以降（特定商取引法／会場優先販売／禁止事項／免責事項）は第5〜8条へ繰り下げ。
- **`kotennavi-p3-17.html`（C-3 精算設定）**：精算メカニクス（月末締め・翌月20日一括精算・精算下限額プリセット・振込手数料の出品者負担）自体はExpress採用でも無変更と確認（Express/CustomともSeparate Charges and Transfers方式で精算タイミングの制御主体は個展なびのまま）。開示レベルの整合のみ `.p114-privacy-note` に「精算処理は決済パートナーであるStripe社を通じて行われます。」を追加。

### 未反映（実装着手時に対応）

- オンボーディング最終ステップへの「Stripeの利用規約に同意して連携」ボタン（embedded onboarding起動）自体はまだ未設置。現状は文言での予告のみ。
- p3-17の振込先口座（`#p317BankName`/`#p317Branch`＝自由入力）：Express採用でも個展なび側フォームのまま維持でき、`external_accounts` APIへ個展なびが送信する形で問題ない。
- 法人番号など法人ギャラリー向け追加情報の要否：Express採用でも未解決の別課題として残る。
- p4-17（ギャラリー版・未作成）作成時、`liaison-settlement`のSET-07/08は自動的に引き継がれる（p3-17と同じ`renderQA`呼び出しを踏襲すればよい）。
