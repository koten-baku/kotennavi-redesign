# LIAISON+ 取引状態 詳細仕様

## 状態名の付随ルール

- ステップノードラベル（6段階・両側共通）：申込 / 購入確定 / 支払 / 発送 / 受取確認 / 完了確認（行為名・「待ち」を付けない）
- ログイベント名：購入申込受付 / 購入確定・送料確定 / 支払い完了 / 発送完了 / 受取確認・評価入力 / 取引完了確認 / 申込キャンセル
- 期限の呼称：S1=確定期限 / S2=支払期限 / S3=発送期限 / S4・S5=確認期限（「取引期限」は使わない）
- 確定期限のルール：実会場優先のため **会期終了7日後または申込7日後の遅い方**（2026-06-27 改訂。旧「会期終了3日後または申込3日後」は使用禁止）。**期限超過時の挙動＝その作品を自動で出品取消し、申込者全員にキャンセル通知（次の申込者へ繰り上げない＝申込者飛ばし防止）。確定期限切れは出品者マイページに記録**
- 発送期限のルール：展示作品は会期終了後の引渡しが多いため **会期終了後7日または支払後7日の遅い方**（「支払いから14日以内」は誤り・使用禁止）
- 「在庫確認」は状態名としては使わない。操作説明の動詞句としてのみ使用可（例：「会場在庫を確認して購入を確定してください」）
- **S0「申込済」は購入確定待ちとは別状態**：申込直後〜申込ID順が到来するまでの待機状態。**確定期限を持たず（表示もしない）・取引ワークスペース（p5-15）に入れない**。この段階のキャンセルは一覧（p5-14）で行う。申込ID順が到来すると**システムが自動で「購入確定待ち」へ遷移**（前の申込者のキャンセル/確定で繰り上げ）、確定期限が発生・表示され、ワークスペースに入れる。バッジはニュートラルグレー（進行に本人操作を要さない待機のため）
- **「N番目／全M人」等のキュー順位表示は廃止**（申込ID＝順位と誤認されるため）。一覧（p5-14）の状態帯は **申込ID#N を軸に表示し、現在の申込総数は申込IDへ括弧併記**（`申込ID#N（全M件）`）＝"申込"の語の重複を避けスマートに。申込済行＝`申込済　申込ID#N（全M件）　YYYY.MM.DD`、購入確定待ち行＝`購入確定待ち　申込ID#N（全M件）　YYYY.MM.DD　確定期限 …`（総数を出すのは申込済・購入確定待ちのみ）、支払待ち以降＝`申込ID#N` のみ（総数なし）。**申込日は「申込日」等のラベルを付けず日付のみ**で置き、文脈（申込済・購入確定待ち＝申込直後の状態）で申込日と読ませる（確定期限は「確定期限」ラベル付きなので混同しない）。個別ページ（p5-15 ワークスペース）に総数・順位は表示しない（申込ID#N のみ継続性のため表示）
- **申込IDの表記は「申込ID#N」で統一**（購入者接点＝p5-14/p5-15、取引ログ＝p3-16/p4-16/p5-15、取引デスクの購入者カード＝p3-16/p4-16 `.p316-purchase-buyer__apply-no`）。旧「申込 #N」は使わない。**例外＝一覧コンソール（p3-15/p4-15）**は「申込者 M件」ラベルで総数が別途出るため、コンパクトな「#N」を安定IDとして継続使用
- **状態strip内の状態バッジ表示は「待ち」を外した行為名**（S1=購入確定 / S2=支払 / S3=発送 / S4=受取確認 / S5=完了確認＝ステップノードと共通。終端は 取引完了 / キャンセル済）。「待ち」はターンラベルが担う。**自分の番のターンラベルは命令形CTAで必要操作を明示する**（S1=購入を確定してください / S2=お支払いにお進みください / S3=作品を発送してください / S4=受取を確認してください / S5=取引完了を確認してください）。相手の番は「○○の△△待ち」。**自分のターンで状態名が「待ち」に見える違和感を解消するための表示ルール。** 正式状態名（〜待ち）は一覧・ログ・説明文など**ターンラベルを伴わない単独表示**では引き続き用いる（テーブルの「正式状態名」が canonical）。
- **一覧ページの状態ラベル（取引一覧・LIAISON+コンソール：p3-15 `.p315-txn-row__status` / p4-15 同 / p5-14 `.p514-aw__strip-label`）は期限を同じラベルにバンドルする（「○○　期限 2026.xx.xx」）ため、ターンラベルを持たない。** この文脈では **自分のターンの行は命令形CTA**（S1=「購入を確定してください」/ S2=「お支払いにお進みください」/ S3=「作品を発送してください」/ S4=「受取を確認してください」/ S5=「取引完了を確認してください」）で意味を明確にし、**相手のターンの行は「〜待ち」**（支払待ち・受取確認待ち・購入確定待ち＋申込ID#n 等）のまま残す。**申込済（S0）の行はターンも命令形も持たず「申込済　申込ID#n（全M件）　日付」のみ**（日付は「申込日」ラベルを付けず日付だけで申込日と読ませる・ワークスペース導線なし・キャンセルは一覧で完結）。strip（ターンラベルあり）とは扱いが異なる点に注意。**出品者コンソール（p3-15/p4-15）の申込者リストでは申込ID#n・総数（申込者 M件）・購入者名が別カラムで出るため、S0 行の `.p315-txn-row__status` セルは「申込済　申込日」のみ**（例：`申込済　2026.02.26`。旧アドホック名「待機中」は使わない＝S0 の客観名は出品者・購入者とも「申込済」で統一）。同行はターンバッジ・取引デスク導線を持たない（順番待ちで出品者の操作対象外のため）。

## 状態strip（`.p515-status__head`）の書式（取引4ページ共通・p3-16/p4-16/p5-15）

- レイアウト＝`[状態バッジ][ターンラベル]` を左寄せ、`一つ前の終了日時（.p515-status__deadline）` を右寄せ（`margin-left:auto`）。DOM順は バッジ→ターンラベル→日時で統一。
- **状態バッジ（`.p515-status__badge`）の文言は行為名のみ（購入確定 / 支払 / 発送 / 受取確認 / 完了確認）で「待ち」を付けない。**「待ち」はターンラベルが担う（相手の番＝「○○の△△待ち」／自分の番＝命令形CTA「作品を発送してください」等＝必要操作を明示）。終端のみ 取引完了 / キャンセル済。単独表示（一覧・ログ）の状態名は正式名（〜待ち）を使う。
- **色は「誰の番か（ターン）」で決まる**：strip背景・状態バッジ・ターンラベルの3要素を同色で付与。`.p515-status--my-turn`＝ページアクセント（p3インクブルー/p4コッパー/p5ピンク）、`.p515-status--waiting`＝グレー。状態の違いはバッジ文言が担い、色では区別しない。
- **ターンラベル（`.p316-turn-label`）は背景なし**（色付きテキスト＋アイコンのみ）。バッジは塗り、ターンラベルは非塗りで役割を区別。
- 状態別バッジ色（`--new/confirmed/paid/shipped/confirming`）は持たせない（ターン色が上書き）。終端のみ `--done`（緑）/`--cancelled`（グレー）が個別色。
- 「一つ前の終了日時」＝S1:申込 / S2:確定 / S3:支払 / S4:発送 / S5:受取確認 / 完了・キャンセル:その確定日。

## 取引期限アラート（`.ktn-txn-alert` / `.p316-action-deadline__soon`）

取引4ページ（p3-16 / p4-16 / p5-15）の**要対応（自分の番＝my-turn）フェーズ**で、一定期間操作がない場合に画面へ出す期限アラート。canonical は `kotennavi-common.css`（`.ktn-days-chip--urgent` 直後 L10787〜）、デモは各取引デスクのデモバー「期限：」トグル。

**表示要素（2段階。第2段階の意味は状態により「超過」または「最終警告」。下表「状態別の段階設計」参照）：**

| 段階 | 表示要素 | クラス | 見た目 |
|---|---|---|---|
| 間近（near） | 期限が迫っている注意書き | `.p316-action-deadline__soon`（`.is-on` で表示） | 赤ドット＋赤文字 1行。`.p316-action-deadline` 内の `__note` 直後に置く |
| 超過／最終警告（overdue） | バナー | `.ktn-txn-alert`（`.is-on` で表示） | 赤枠＋淡赤背景＋警告三角アイコン＋タイトル＋本文。`.p515-status` 直下、`.p515-status__head` の**前**に置く。自動キャンセル型（new/payment）はこのバナーを「最終警告」として使い、自動確定型（receipt/confirming）はバナーを持たない |

両段階共通で `.ktn-days-chip` が `.ktn-days-chip--urgent`（赤塗りチップ）化し、状態strip右肩の `.p515-status__deadline` が `.p515-status__deadline--alert`（赤文字）化する。

**表示/非表示は `.is-on` クラスで制御（`hidden` 属性は使わない）：** クラス側 `display:flex` が UA の `[hidden]{display:none}` を同詳細度・後勝ちで上書きしてしまうのを避けるため、デフォルトを `display:none` にして `.is-on` で開く。

**my-turn フェーズの定義（このフェーズでのみアラートが出る。相手の番＝waiting では出ない）：**
- 出品者デスク（p3-16 / p4-16）：`new`（S1購入確定）/ `paid`（S3発送）/ `confirming`（S5完了確認）
- 購入者デスク（p5-15）：`payment`（S2支払）/ `receipt`（S4受取確認）

**状態別の段階設計（判断軸＝「期限到達で状態が自動遷移するか＝超過状態がこの画面に現れ得るか」。不可逆な不利益の有無ではない）：**

期限到達で状態が自動遷移する状態は、超過状態のページが本人に見える前に画面が消える（キャンセル）か次フェーズへ移る（自動確定）ため、**「過ぎています」バナーは原理的に表示され得ない**。よって超過段階を持たせず、期限前の警告で完結させる。自動遷移しない状態のみ超過バナーを持つ。

| 状態 | 期限到達時の挙動 | 段階 | 理由 |
|---|---|---|---|
| 出品者 `paid`（S3発送）（p3-16/p4-16） | **自動遷移しない**（管理者通知＋購入者キャンセル申請可になるが、出品者は state に留まりページ継続） | 間近→超過（標準） | 超過状態が出品者デスクに実在するため超過バナー表示に矛盾なし |
| 出品者 `new`（S1購入確定）（p3-16/p4-16）／ 購入者 `payment`（S2支払）（p5-15） | **自動遷移＝キャンセル**（影響大）。S1＝作品を自動で出品取消し申込者全員にキャンセル通知（次の申込者へ繰り上げない）。S2＝申込が自動キャンセル。いずれもこの取引ページにアクセス不可になる | **2段階とも期限前**（間近→最終警告） | 「過ぎています」状態は画面に現れない。第2段階は「超過」でなく最終警告：バナー「まもなく確定期限です／まもなく支払期限です」、チップ「期限超過」→「本日中」（`OVERDUE_CHIP={new:'本日中'}`〔p3-16/p4-16〕・`{payment:'本日中'}`〔p5-15〕） |
| 購入者 `receipt`（S4受取確認）（p5-15）／ 出品者 `confirming`（S5完了確認）（p3-16/p4-16） | **自動遷移＝確定**（影響小）。自動受取確認（S4）／7日経過で自動完了確定（S5）で取引継続 | **期限前1段階のみ**（間近）・超過バナーなし | 超過しても取引は前進し影響小。**S4とS5は同位置付け**。超過バナー（`.ktn-txn-alert`）を持たず soon note 1段階のみ。overdue レベルが来ても near に畳む（p5-15 `NO_ESCALATE={receipt:1}`／p3-16・p4-16 `NO_ESCALATE={confirming:1}`） |

- S1の「次の申込者へ繰り上げない（作品を自動で出品取消・申込者全員にキャンセル通知）」は、出品者が期限切れを使って申込順を飛ばす（特定購入者の選定）ことを防ぐための仕様。ガイド p70-2 / p70-12、各取引デスクのS1パネルに明示。詳細は handoff-decisions 7章（2026-06-27）。

**JS（デモ実装・各ページ末尾）：** `MY_TURN` マップ＋`NO_ESCALATE`（receipt / confirming を near に畳む）＋`OVERDUE_CHIP`（自動キャンセル型の最終段階チップを「本日中」に。p3-16/p4-16＝`{new:…}`／p5-15＝`{payment:…}`）＋`window.txnUrgency`＋`applyUrgency()`＋`window.setUrgency(level)`。`setDemoState` の末尾で `applyUrgency()` を呼ぶ。`applyUrgency` は毎回全リセット後、`MY_TURN[setDemoState.curKey]` かつ level≠normal のときだけ現在表示中の `.p515-status:not([hidden])` ブロックに適用。`near`→chip「あと1日」＋soon、`overdue`→chip `OVERDUE_CHIP` 該当は「本日中」／他は「期限超過」＋banner。

**本番（React CSR）の扱い：** デモはデモバートグルで段階を切替えるが、本番は API/Drupal が返す期限値（タイムスタンプ）と現在時刻から段階をクライアント側で自動算出する（間近の閾値・超過判定はクライアントで計算）。HTML 構造とクラス（`.is-on` トグル）はそのまま流用可。

**待ち側ナッジ（`.p515-status__waiting-nudge`・取引4ページ共通）：** my-turn 側に催促アラートが出るのと連動して、**相手の番（waiting）フェーズ**の相手側画面に「システムが相手に確認を促している」ことを中立的に伝える1行通知（メルカリ式）。**期限の数字・段階・「催促」表現は出さない**（運用後の期限チューニングとの表示齟齬を避け、管理者への問い合わせを増やさないための方針。詳細＝handoff 7章 2026-06-27）。文言は「システムから{相手}へ{行為}のご確認をお願いしています。」の受動・中立形。見た目は赤系の `.ktn-txn-alert` と区別し `var(--paper)` 背景＋ヘアライン枠＋ベルアイコン（muted）。表示は `.is-on`。発火＝`WAITING_NUDGE` マップ（出品者 p3-16/p4-16＝`{confirmed:S2購入者の支払待ち, shipped:S4購入者の受取確認待ち}`／購入者 p5-15＝`{paid:S3出品者の発送待ち}`）にあり level≠normal のとき、現在表示中ブロックの nudge に `.is-on` を付与（near/overdue 同一・段階なし）。`applyUrgency` 冒頭で全 nudge をリセットし、`WAITING_NUDGE` 該当時は my-turn 分岐の前で return。**S5（出品者の完了確認待ち）と S1（出品者の確定待ち）は対象外**：前者はスコープ外、後者は購入者デスク（p5-15）に applied 状態ブロックが存在しないため（本番で S1 購入者ビューを設ける場合は要追加）。本番は「相手の期限 − 現在時刻」が催促閾値に達したら表示。
